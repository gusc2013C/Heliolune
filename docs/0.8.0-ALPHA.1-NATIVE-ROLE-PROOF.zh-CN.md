# Heliolune 0.8.0 alpha.1：Native V2 角色路由实测

2026-08-08 在 Codex Desktop `26.803.5235.0`、内核 `0.147.0-alpha.6.5` 上完成 P0。

## 结果

| 路由 | 实际角色 | 实际模型 / effort | 后端 | 结果 |
| --- | --- | --- | --- | --- |
| Sol → owner | `heliolune_luna_owner` | `gpt-5.6-luna` / `max` | V2 | 通过 |
| Luna → peer | `heliolune_luna_peer` | `gpt-5.6-luna` / `max` | V2 | 通过 |
| Luna → terminal | `heliolune_spark_terminal` | `gpt-5.3-codex-spark` / `medium` | V2 | 通过 |

所有 spawn 都显式使用 `fork_turns="none"`，且未提供 `model` 或 `reasoning_effort`。落盘 rollout 同时确认 `agent_role`、真实模型、effort 与 `multi_agent_version=v2`，因此不是 Terra 回退或同名任务假阳性。

## 一个重要启动边界

添加 `.codex/config.toml` 前已经存在的任务返回了：

```text
unknown agent_type 'heliolune_luna_owner'
```

同名 `task_name` 只能产生 `agent_role=null` 的 Sol child。创建新 Codex 任务后，项目角色被加载并正常路由。因此安装或修改角色后必须新建任务，不能在旧任务中把失败误判为运行时不支持。

## Token 观察

`fork_turns="none"` 清除了对话历史，但不会清除系统、插件、Skill 与工具定义。最小 owner marker 首轮仍使用 17,860 total tokens；peer 为 17,736，Spark 为 16,562。owner 在一次 follow-up 和多次生命周期工具调用后的累计输入为 128,776，其中 107,008 为 cached input。

结论是：Native V2 消除了 0.7 的 MCP schema、DAG、lease 与独立 app-server 成本，但 child 仍有显著固定上下文。0.8 必须复用一个 owner 与一个可选 Spark terminal，并把任务批量化；每条命令重新 spawn Spark 不会节省额度。

安装后前向测试还发现 root 与 owner 重复执行 preflight，并伴随整目录内容转储。alpha.1 随后把 preflight 改为 compact contract evidence，并在 owner role 中禁止重复 preflight 与广泛内容转储。

强制把单文件只读任务交给 Luna 后，又定位到第二个额外消耗源：Windows shell 启动与引号错误造成的重试。仅给出通用 Windows 指引时仍出现 4 次仓库工具调用，累计 125,467 tokens。最终 owner role 固化为系统 `cmd.exe` + `type` 的确定性单文件模板。落盘 rollout `019fdfe0-9c7e-7a70-9070-981efe878bf6` 证明：真实 `Luna/max/V2`、只有 1 次仓库工具调用、无改动，累计 57,484 tokens；相较 4-call 版本下降 54.2%，相较更早的 5-call 版本下降 57.6%。这个微型任务是为隔离开销而强制委派；正常路由仍应把单文件小任务留给 Sol，因为剩余固定 Desktop 上下文占主导。

完整机器可读证据见 [`benchmarks/results/0.8.0-alpha.1-native-role-proof-r1.json`](../benchmarks/results/0.8.0-alpha.1-native-role-proof-r1.json)。下一阶段应先做无 Spark 的 0.8 alpha.2 单 Luna writer 真实工程匹配测试。
