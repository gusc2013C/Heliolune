# 0.6.3 运行时与后端诊断

[English](0.6.3-RUNTIME-DIAGNOSTIC.md) · 简体中文

## 目的

本轮 demo 只用于排查 Heliolune，不是生产项目。新的无依赖 Python 仓库 ParcelPulse 规定了确定性库存事件对账引擎、JSONL loader、CLI 和 12 个公开测试；另有 8 个隐藏测试放在仓库外，只在集成后由 Sol 执行。

本轮同时复现了用户看到的“重新变成串行 Luna，并出现 Codex 窗口而不是只有悬浮窗”。

## 串行与可见 worker 回归的根因

当前 Codex task 在新版插件源码安装前就加载了旧 Heliolune MCP。其工具面仍有旧 `initialize_pool`/`run_task` 行为，并没有新的 `runtime_info`。已存在 task 内的 MCP 进程和工具 schema 不会因为编辑或重装插件而热替换，因此源码已经并行并不代表当前 task 已切换。

0.6.3 增加不调用模型、失败关闭的预检。任何付费任务开始前，skill 要求运行时明确报告：

- 版本 `0.6.3`；
- 默认 `speed-first`、并行度 4；
- burst thread 为 ephemeral；
- standalone app-server 隐藏；
- Windows 使用原生状态窗。

任一不匹配都会在启动 Luna 前停止，并要求新建 Codex task 或重启应用。standalone app-server 使用隐藏启动，worker thread 为 ephemeral，Windows 自动可见的 worker 界面只有 WPF Leader 悬浮窗。

## 发现并修复的问题

1. 并行 contract lane 会把普通歧义作为 `needsSol` 并中断 writer。现在只有 `status=blocked` 且非空决策确实属于 Sol 保留边界时才能触发。
2. 只读 reviewer 天然读取互相隔离的 base snapshot，原先却把初始文件状态包装成与并发 owner patch 冲突。现在 reviewer 与 Leader 都明确这是基线指导，实际路径和 integration record 才是 artifact 状态的权威来源。
3. Codex 命令环境选择了失效的 `C:\Users\Infplane\.gaia\venv\Scripts\python.exe`，其 uv Python 已不存在。Heliolune 现在通过官方 shell environment policy 优先使用 Codex bundled Python、Node 和 Git，同时保留正常 host PATH 回退。
4. 360 秒任务原先预留 90 秒做结构化收尾，导致最后一次测试时间不足。默认 reserve 改为 40–60 秒，原 turn 获得 10–20 秒比例化 schema 收尾宽限。
5. Luna 把不可见 hidden tests 当成未完成 acceptance，提供的测试全部通过后仍返回 `partial`。现在 scoped 工作和所有已提供、可运行检查在最后一次修改后通过即可 `completed`；未知隐藏测试只作为 Sol 风险。

## 最终运行

| 指标 | 结果 |
|---|---:|
| 路由 | 4 路 `speed-first` |
| Worker / Leader 思考强度 | Luna `max` / Luna `high` |
| Contract guard | 并行；未触发 |
| 集成 | 安全应用；2 个变更路径 |
| 墙钟时间 | 337.050 秒 |
| worker 墙钟 / worker 时间总和 | 318.448 秒 / 698.186 秒 |
| Luna 输入 / 缓存输入 | 134,910 / 94,208 |
| Luna 输出 / 推理输出 | 11,118 / 8,458 |
| worker 输入缓存率 | 69.83% |
| Luna 实测费用 | 0.584154 价格单位 |
| 历史校准 Sol-only 预测 | 2.396642 价格单位 |
| 预估节省 | 75.63%（方向性） |
| 公开验收 | 12/12 |
| 仓库外隐藏验收 | 8/8 |

owner 完成后，Heliolune 只有在 clean state、scope、completion、overlap 和 Git apply gate 全部通过时才应用 `parcelpulse/engine.py` 与 `parcelpulse/cli.py`。随后 Sol 独立执行公开测试，以及 UTC 偏移、生成器不可变、拒绝原子性、signed adjust、非法类型、确定性重复、iterable JSONL、stdin 和缺文件检查，总验收 20/20。

## 结论

最终运行证明 Heliolune 对有界、多文件后端任务具有应用价值：Luna/max 以较低 worker 费用产生正确实现，Sol 保留最终验收。但它不是速度胜利；317 秒 owner 仍是关键路径，并行审查提高覆盖面却没有让墙钟短于 writer。因此该结果支持“费用优先、进度可见”的使用场景，不代表 Heliolune 普遍快于 Sol-only。
