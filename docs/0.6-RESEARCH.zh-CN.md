# Heliolune 0.6 工程报告：Token 与并行速度档位

本文记录用于验收 Heliolune 0.6.0 的证据；0.5.2 数据作为历史基线保留。

## 预研问题

1. 0.5.2 还有哪些可避免的模型 token 或墙钟开销？
2. 不把 Luna 缓存命中当作目标时，4 个或 8 个冷 Luna 能否在质量相近时显著加速？
3. 能否把结论做成两个简单档位，同时仍由 Sol 掌握规划和保留决策？

## 0.5.2 Token 与可靠性审计

0.5.x 持久化 dashboard 记录了 12 次成功任务和 4 次失败，worker 墙钟合计 960.155 秒；用量为 383,593 input、317,440 cached input、11,017 output，input cache rate 为 82.75%，Luna 估算费用为 0.819995 price units。

费用构成比表面缓存率更重要：

| 组成 | Price units | 占比 |
|---|---:|---:|
| 未缓存输入 | 0.330765 | 40.34% |
| 缓存输入 | 0.158720 | 19.36% |
| 输出 | 0.330510 | 40.31% |

共享 supervisor/Leader lane 的两次未缓存 turn 消耗 0.141155（17.21%）。integration lane 的 0.512369 中，输出占 0.300690（58.69%）。因此只优化缓存不足以解决问题；终态可靠性、可选模型 turn、输出体积和 Sol 可见的 MCP schema 同样关键。

本轮复现了决定性的可靠性问题：真实 worker 已发出 `turn/completed`，但 0.5.2 只匹配 `params.turn.id`；当前 App Server 也可能通过顶层 `params.turnId` 标识同一通知。活动追踪看到了完成事件，终态 waiter 却没有匹配，于是产生 `hard_timeout_active`、无意义的 180 秒等待和 finalization 失败。预研分支统一识别两种通知形状，并保留有界 completed-turn 缓冲以关闭 response/waiter 竞态。针对性回归现在约 150–170 ms 完成，不再走到测试硬超时。

0.6.0 还做了以下 token 优化：

- 删除内联 MCP App 与仅供 App 使用的 `job_status` 工具；Windows 原生悬浮窗成为 Heliolune 唯一绘制的实时界面。
- 删除重复公开的阻塞式 `run_task`；Desktop 统一使用 `start_task` 或 `start_batch`，随后只调用一次 `await_task`。
- 从常用 token-first schema 移除低频 supervision/finalization/reporting 调试旋钮，内部安全默认值仍保留。
- 序列化工具定义从改动前 token-first 界面的约 2,520 个近似 token，下降到包含 speed-first 在内的完整 0.6 工具面约 1,557 个，下降 38.2%；仅 speed-first 工具面约 1,074 个。这里使用字符数除以四的粗略估算；MCP 边界仍无法观测当前 Sol controller 的实际用量。

## 并行基准方法

同一组 8 个相互独立的只读代码审计 workstream 使用相同输出 schema，分别以 1、4、8 并发运行。每个测量档位都新建 Luna/max worker thread，不要求持久 lane 缓存；每组也同样支付一次全新的 Luna/high Leader 汇总 turn。墙钟包含 worker 执行和 Leader 汇总，初始化时间在原始结果中单独记录。

`cacheIgnoredColdEquivalent` 把所有输入 token 都按 Luna 未缓存输入费率计价，即使服务实际报告了缓存命中。这样可以回答“不考虑缓存”的费用问题，而不虚构 API 可以关闭缓存。

## 结果

| Luna 并发数 | 样本数 | 墙钟 | 相对 1 路加速 | 质量评分 | 忽略缓存的冷等价费用 |
|---:|---:|---:|---:|---:|---:|
| 1 | 1 | 200.769s | 1.00× | 100% | 0.890920 |
| 4 | 2 | 52.064–53.627s；均值 52.846s | 3.80× | 90–95% | 均值 0.816648 |
| 8 | 2 | 36.488–73.225s；均值 54.856s | 3.66× | 95% | 均值 0.821255 |

4 路得到了稳定、接近线性的加速。8 路创造了最快单次结果（5.50×），也出现了最慢并行结果（2.74×），原因是一个 worker 成为 67.6 秒长尾。并行样本只有两次，因此方差比均值更重要：8 路适合作为显式低延迟实验，不适合作为默认值。

自动质量评分偏保守。并行组的扣分来自严格字符串检查，以及一道 scope 只允许读取 `status-window.mjs`、却要求证明 server 已删除内联 UI 的问题；诚实的 `uncertain` 被扣分，实际暴露的是 benchmark scope 缺陷。两次完整 MCP smoke 中的 4 个 workstream 全部完成，共享 Leader 均返回结构化报告。

三次 4 worker 端到端 MCP smoke 分别耗时 44.137、49.607 和 43.843 秒。worker 墙钟为 29.883、35.264 和 29.681 秒，worker 时长求和为 99.828、111.832 和 102.530 秒；共享 Leader 分别增加 14.252、14.340 和 14.159 秒。第二次 smoke 成功显示原生 WPF 悬浮窗并写入 ready marker，server 没有声明内联 MCP App resource 或 output template。最后一次使用精简后的公开 `start_batch` schema，4 个 workstream 全部完成，Luna 估算费用为 0.225093 price units。

## 0.6 档位

### Token 优先

- 使用 `start_task`，随后只调用一次 `await_task`。
- 每个任务只使用一个功能亲和 Luna/max owner。
- 持久化 `core`、`tests`、`integration`、`verifier`，另有一个共享 Luna/high Leader。
- verifier 与 Leader 自适应触发，不进行模型轮询。
- 支持有界分析、实现和修复。
- 优化稳定前缀、session 复用、紧凑 schema 和最小充分结果。

### 速度优先

- 使用 `start_batch`，随后只调用一次 `await_task`。
- Sol 必须预先给出 2–8 个独立 workstream，各自有 scope 与验收条件；Luna 不得规划或拆解父任务。
- 默认 4 个 Luna/max burst worker；8 个必须显式选择，且仍属实验能力。
- 一个共享 Luna/high Leader 负责核对所有终态并压缩上报，但不读取仓库、不解决分歧、不做最终验收。
- 每个 workstream 有独立硬截止和失败隔离；一个长尾可使 batch 变为 partial，但不会丢弃其他已完成结果。
- 优先把 workstream 缩到 90 秒内，但有界任务允许最长 600 秒。一个共享 Luna/high Leader session 会合并同时发生的 90 秒检查并逐 slot 给出存活建议；后续排队波次可复用同一 session 再做一次有界检查。它不规划、不重新分配工作，也不轮询。终态时复用同一 warm Leader 压缩整个 batch。
- 只读 burst session 可以复用；每个 mutating workstream 使用 fresh Luna/max session，并进入独立 detached Git worktree。
- 修改 batch 要求仓库根目录干净、仍处于原提交 `HEAD`，且使用狭窄、仓库相对、两两不重叠的 scope。Heliolune 收集 full-index Git patch，拒绝越界或重叠路径，先执行 `git apply --check --index`，然后整体应用，并把主工作树 index 保持为 unstaged 供 Sol 审查。
- 任一 worker partial/failed、主 `HEAD` 改变或主工作树新增脏修改都会阻止整个 apply。主 checkout 保持不变，patch 证据路径会上报给 Sol；系统不会复制仓库。

## 并行写入 smoke

发布 smoke 创建了一个临时 Git 仓库，把互不重叠的 `alpha.txt` 和 `beta.txt` 分给两个真实 Luna/max worker。每个 worker 只修改自己的 detached worktree，Heliolune 随后验证两个 patch，并安全应用到干净的主 checkout。

| 指标 | 结果 |
|---|---:|
| Batch 状态 | completed |
| 安全集成 | 已应用 `alpha.txt`、`beta.txt` |
| Apply 后主 index | clean / unstaged |
| 剩余 Git worktree | 1（仅主 worktree） |
| Worker 墙钟 / 时长求和 | 27.428s / 50.702s |
| 共享 Leader | 8.110s |
| 端到端墙钟 | 35.541s |
| Luna 用量 | 44,690 input；28,160 cached；666 output；203 reasoning |
| Luna 估算费用 | 0.116710 price units |

单元测试还覆盖越界路径拒绝、dirty main 拒绝、`HEAD` 变化拒绝、patch 证据保留、untracked 文件集成、worktree 清理以及最终 index unstaged。

## 决策

该功能在明确约束下可行。4 路 speed-first 能显著缩短墙钟；其冷等价费用均值比单 worker 只读样本低 8.34%，两次 4 路结果相对串行分别低 12.26% 和 4.42%。由于串行只有一个样本，这只能说明“费用相当”，不能承诺普遍节省。8 路保持 opt-in，直到更多重复实验能证明长尾更稳定。0.6.1 将 4 路提升为小任务也适用的产品默认：一个隔离写 owner 可以与有意义的只读 contract、测试/边界和风险 workstream 并行。token-first 只保留给 dirty/非 Git 的 mutating checkout、无法隔离的写入或严格顺序依赖。

worktree gate 已解决当前并行文件写入的安全问题，并且没有在主 checkout 中开放并发写。后续还应增加多轮混合规模基准、明确的服务并发诊断、batch dashboard 分位数和跨平台状态 UI 覆盖。

本轮被测 workstream 都在 90 秒管理检查点之前完成，因此费用表包含终态 Leader 汇总，但不包含长任务额外管理 turn。长 batch 管理目前由调度、prompt 边界、watchdog 与共享 session 测试覆盖；其增量费用仍需在正式发布前做专门 benchmark。
