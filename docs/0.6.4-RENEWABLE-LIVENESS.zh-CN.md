# 0.6.4 可续租存活验证

[English](0.6.4-RENEWABLE-LIVENESS.md) · 简体中文

## 目的

本版本不再把墙钟时间当作 worker 失败条件。Heliolune 仍鼓励把 workstream 拆到约 90 秒规模，但活动工作会通过可续租存活检查继续运行。只有持续静默，而不是运行时长，才会唤醒 Luna/high Operations Leader。

## 实际策略

- `checkpointSeconds` 只控制首次存活观察，不是执行截止。
- 近期 app-server 活动在本地直接续租，不产生 Leader turn。
- 首次检查后每 30 秒重复检查。
- 持续静默才唤醒一个共享 Luna/high Leader。
- 只有高置信度 `interrupt` 判断能中止 worker；低/中置信度、模糊判断或 Leader 失败都会继续。
- 运行中 job 不再有墙钟 expiry；owner 编排进程退出仍是 orphan 终态失败。
- 活动工作不会因时间被 steer 收尾。只有 completed turn 返回非法 JSON 时，才允许一次同 thread、no-tools Luna/high schema repair。
- 4/8 worker batch 使用共享队列；任一空闲 slot 会立即领取下一项 Sol 已定义 workstream，不等待较慢 sibling。
- 常规 `start_task` schema 不暴露任何时间字段；高级 `start_batch` 只保留可选的首次检查点控制。
- Codex 要求的有限 MCP transport 保护对单次 await 设为 24 小时；它不会进入后台 job，也不会取消活动 worker。

## 自动化回归

完整无依赖 Node 测试 72/72 通过。新增关键场景覆盖：

- 活动 fake app-server turn 超过旧硬截止后仍正常完成；
- 多轮可续租检查后才以高置信度中止静默 stall；
- 缺失 `turn/completed` 时仍从 completed final-answer item 恢复；
- owner 进程存活时忽略旧 job expiry；
- 长 sibling 未完成时，空闲 slot 已领取排队任务；
- PowerShell 5.1 状态读取、orphan 界面恢复、worktree 隔离、patch 安全、费用与 MCP schema。

## 真实 Luna 运行

| 场景 | 结果 | Worker 墙钟 | 最慢 worker | Luna 估算费用 |
|---|---:|---:|---:|---:|
| 四路只读 / 四 slot | 4/4 完成 | 57.343s | 56.688s | 0.234721 |
| 双隔离写入 / 四 slot | 2/2 完成并安全应用 | 32.415s | 31.243s | 0.122840 |
| 五路只读 / 四 slot，30s 检查点 | 5/5 完成 | 49.494s | 48.871s | 0.271518 |
| 八路只读 / 八 slot，30s 检查点 | 8/8 完成 | 93.992s | 92.968s | 0.497546 |
| 默认 `start_task` / 四 slot | 4/4 完成 | 219.551s | 218.899s | 0.651162 |

五路运行是直接的续租与队列测试。首次检查点为 30 秒，但 `window` 在 37.972 秒、`batch-safety` 在 48.871 秒自然完成。`burst-2` 完成 `profiles` 后领取第五项 `job-records`，当时其他 sibling 仍在运行。所有 worker 都有近期活动，因此 `leaderManagementChecks=0`；终态仍由共享 Leader 汇总一次。

隔离写入运行在 fresh detached worktree 中修改两个互不重叠文件，安全集成两份 patch，没有留下 staged 路径，并清理到只剩主 worktree。

八路运行也在多轮 30 秒检查后自然完成，`leaderManagementChecks=0`，因为近期活动在本地为每个活动 lease 续租。92.968 秒长尾证明续租正确，同时也支持继续把 8 路作为 opt-in，而不是替换默认 4 路。

最终默认快速入口复测给出了最直接的回归证据：两个 worker 分别运行 162.639 和 218.899 秒，四路全部自然完成，且 `leaderManagementChecks=0`。旧 120/180 秒 worker 边界会把这次运行误判为失败。紧凑原始结果保存在 [`benchmarks/results/0.6.4-renewable-fast-start-r1.json`](../benchmarks/results/0.6.4-renewable-fast-start-r1.json)。

Schema 压缩使安装后的 pool 工具面约从 1,447 降到 1,151 token（20.46%），常规 `runtime_info` + `start_task` 从 643 降到 480（25.35%），高级 batch schema 从 579 降到 447（22.79%）。

## 测试中发现的问题

第一次较宽的源码审查正确超过了 30 秒检查点，但 benchmark harness 自身仍在 210 秒后停止等待并杀死子 server。这不是 Heliolune worker timeout。现已删除该 harness 截止，并把诊断拆成更小 workstream，得到上述决定性复测结果。

最终 Luna review 还产生了一条错误候选风险，声称 `await_task` 仍暴露 `timeoutSeconds`。Sol 直接检查与 MCP schema 回归都证明该字段不存在。它没有影响执行或验收，但暴露了汇总质量风险：batch Leader prompt 现在明确要求把未证实 worker 风险保留为候选发现、不得提高严重级别，并说明 Leader confidence 不是正确性结论。最终审查仍属于 Sol。

## 结论

本版本把任务尺寸与存活判断彻底分开。小 workstream 仍应优先，因为它能降低长尾并让空闲 slot 更早领取剩余任务；但 productive worker 不会再因为超过尺寸估算而被中止。
