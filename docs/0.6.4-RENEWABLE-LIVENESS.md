# 0.6.4 renewable-liveness validation

English · [简体中文](0.6.4-RENEWABLE-LIVENESS.zh-CN.md)

## Purpose

This release removes elapsed wall time as a worker failure condition. Heliolune now encourages workstreams near 90 seconds but keeps active work alive through renewable liveness checks. Sustained silence, not duration, is the only reason to consult the Luna/high operations Leader.

## Effective policy

- `checkpointSeconds` controls the first liveness observation and is not an execution deadline.
- Recent app-server activity renews locally; it costs no Leader turn.
- Checks repeat every 30 seconds after the first checkpoint.
- Sustained silence wakes one shared Luna/high Leader.
- Only a high-confidence `interrupt` decision stops a worker. Low/medium confidence, ambiguity, or Leader failure continues.
- Running job records have no wall-clock expiry. Owner-process exit remains a terminal orphan condition.
- Active work is not steered to finalize. A completed turn with invalid JSON may use one same-thread, no-tools Luna/high schema repair.
- Four/eight-worker batches consume a shared queue. The first idle slot takes the next remaining Sol-defined workstream without waiting for slower siblings.
- The normal `start_task` schema exposes no timing field. Advanced `start_batch` retains only the optional first-checkpoint control.
- Codex's required finite MCP transport guard is set to 24 hours for the one await call. It does not propagate into the background job or cancel a live worker.

## Automated regression

The complete dependency-free Node test suite passed 72/72. New decisive cases cover:

- an active fake app-server turn completing after its former hard timeout;
- repeated renewable checks followed by a high-confidence silent-stall interrupt;
- a completed final-answer item surviving a missing `turn/completed` notification;
- a legacy expired job record continuing while its owner process is alive;
- an idle slot claiming queued work before a long sibling completes;
- PowerShell 5.1 status parsing, orphan display recovery, worktree isolation, patch safety, pricing, and MCP schemas.

## Real Luna runs

| Scenario | Result | Worker wall | Slowest worker | Luna estimated cost |
|---|---:|---:|---:|---:|
| Four read-only streams / four slots | 4/4 completed | 57.343s | 56.688s | 0.234721 |
| Two isolated write streams / four slots | 2/2 completed and safely applied | 32.415s | 31.243s | 0.122840 |
| Five read-only streams / four slots, 30s checkpoint | 5/5 completed | 49.494s | 48.871s | 0.271518 |
| Eight read-only streams / eight slots, 30s checkpoint | 8/8 completed | 93.992s | 92.968s | 0.497546 |
| Default `start_task` / four slots | 4/4 completed | 219.551s | 218.899s | 0.651162 |

The five-stream run is the direct liveness and queue test. `window` completed in 37.972 seconds and `batch-safety` in 48.871 seconds despite a 30-second first checkpoint. The fifth `job-records` stream was claimed by `burst-2` after that slot completed `profiles`, while other siblings remained active. All workers had recent activity, so `leaderManagementChecks=0`; the terminal Leader report still ran once.

The isolated-write run changed two disjoint files in fresh detached worktrees, safely integrated both patches, left no staged paths, and returned to one main worktree.

The eight-way run also completed naturally beyond repeated 30-second checks with `leaderManagementChecks=0`, because recent activity renewed every active lease locally. Its 92.968-second tail confirms liveness correctness but also supports keeping eight-way opt-in rather than replacing the four-way default.

The final default-fast-path rerun is the strongest direct regression: two workers ran for 162.639 and 218.899 seconds, all four completed naturally, and `leaderManagementChecks=0`. The prior 120/180-second worker boundaries would have made this a false failure. The compact raw result is retained in [`benchmarks/results/0.6.4-renewable-fast-start-r1.json`](../benchmarks/results/0.6.4-renewable-fast-start-r1.json).

Schema compaction reduced the installed pool surface from approximately 1,447 to 1,151 tokens (20.46%), the normal `runtime_info` + `start_task` path from 643 to 480 (25.35%), and the advanced batch schema from 579 to 447 (22.79%).

## Failure found during testing

An earlier broad source audit continued correctly beyond its 30-second checkpoint, but the benchmark harness itself still stopped waiting after 210 seconds and then killed its child server. This was not a Heliolune worker timeout. The harness deadline was removed, and the diagnostic was split into smaller workstreams for the decisive rerun above.

The final Luna review also emitted one false candidate risk claiming that `await_task` still exposed `timeoutSeconds`. Direct Sol inspection and the MCP schema regression proved the field absent. This did not affect execution or acceptance, but it exposed an aggregation-quality risk: the batch Leader prompt now explicitly keeps unsupported worker risks as candidate findings, forbids severity upgrades, and states that Leader confidence is not a correctness verdict. Sol remains the final reviewer.

## Interpretation

The release now separates task sizing from liveness. Smaller workstreams remain strongly preferred because they reduce tail latency and let idle slots pull queued work sooner, but a productive worker is no longer punished for exceeding a size estimate.
