# Heliolune 0.7.0-alpha.2 DAG evaluation

English · [简体中文](0.7.0-ALPHA.2.zh-CN.md)

`0.7.0-alpha.2` implements a safe subset of the roadmap's task-graph and 0.8 scheduling direction. It upgrades alpha.1's telemetry-only task nodes into executable `TASK_DAG_V1` state while retaining start-once/await-once, renewable liveness, detached ownership, native-window closure, and isolated write integration.

## Implemented

- Dependency validation, cycle/missing-node rejection, and deterministic `pending → ready → running → terminal` transitions.
- Read/write leases. Unordered conflicting nodes fail before a model call; read leases may overlap.
- Adaptive event-driven width `1 → 2 → 4`. Four independent READY nodes widen immediately; a candidate challenge opens a second slot only after its producer completes.
- Selection by critical depth, explicit priority, path/repository affinity, and deterministic order.
- Optional queued-node cancellation after all required nodes and `completionQuorum` complete.
- Post-patch challenge nodes bound to `baseRef + SHA-256 candidateFingerprint`, forced onto a different worker slot and given the exact producer worktree without owner reasoning.
- DAG-aware queue, assignment, cancellation, blocked-node, lease, width, utilization, and critical-path telemetry.
- Explicit `throughput` profile; legacy `speed-first` remains an alias and token-first remains the unsafe-isolation fallback.

Alpha.2 rejects chained writers. A successor writer cannot safely see an unintegrated predecessor patch in the current detached-worktree design, so accepting that graph would create false dependency semantics. Child suggestions, speculative straggler hedges, Terra, and learning-based routing are also deferred.

## Real candidate-bound write run

The final real Luna/max graph executed `owner → challenge` against a temporary Git repository:

| Evidence | Result |
|---|---:|
| Total wall time | 371.676s |
| Owner | `burst-1`, 33.383s |
| Width transition | 33.384s, `1 → 2`, `candidate-thread-isolation` |
| Challenge | `burst-2`, 337.349s |
| Candidate fingerprint | `3b17d50d…ca55d1f0` |
| Critical path | 370.732s |
| Usage | 108,215 input / 104,960 cached / 1,675 output |
| Estimated Luna cost | 0.119005 |

The challenge inspected the producer's exact post-patch checkout, used a different thread/slot, and retained the same fingerprint through completion. Integration safely applied only `feature.txt`, left the index unstaged, removed temporary worktrees, and exited the detached runner. The 337-second challenge is a real latency cost; DAG correctness does not itself imply faster completion. An earlier corrected run of the same graph completed in 174.973 seconds with a 140.129-second challenge, reinforcing the long-tail variance rather than a stable latency estimate.

The first candidate run also completed, but review found it widened at 0ms with only the owner READY and reported the challenge kind as `inspect`. Both telemetry defects were fixed, covered by regressions, and the real run above was repeated from scratch.

Final pre-publish review found a second scheduling edge: if a sibling still occupied the alternate slot when the producer completed, the challenge could have reused the newly idle producer slot. Candidate nodes now treat the producer slot as ineligible and wait for another slot. The same review aligned throughput's runtime with its declared 1/2/4/8 schema and removed producer summary/evidence from candidate dependency input; only completion state and fingerprint metadata remain. Focused regressions raised the complete release suite to 121 passing tests.

A separate current-build throughput regression ran two disjoint writers in parallel and completed in 63.067 seconds. Both nodes completed, `alpha.txt` and `beta.txt` were safely applied, the main index remained unstaged, only the fixture's primary worktree remained, and the detached runner exited. This preserves the independent-writer path while chained writers remain deliberately rejected.

After the final cachebuster reinstall, a fresh Codex app-server host smoke completed in 64.771 seconds. `runtime_info` returned the exact alpha.2 version/build/prompt and `TASK_DAG_V1` capabilities; a real adaptive worker completed, independent await returned terminal state, the Simplified Chinese native panel closed automatically, and the detached runner/app-server tree exited.

## Matched adaptive versus throughput

The same four-node renewable-liveness audit was run once per route:

| Route | Wall | Slowest node | Worker sum | Leader | Estimated cost |
|---|---:|---:|---:|---:|---:|
| Adaptive DAG | 338.958s | 317.408s | 939.217s | 20.976s | 1.010623 |
| Throughput | 465.561s | 437.035s | 1,172.280s | 27.951s | 0.802499 |
| Adaptive observed delta | **-27.19%** | **-27.37%** | **-19.88%** | **-24.95%** | **+25.93%** |

Both routes opened four slots at 0ms and assigned the same node order. Therefore the faster adaptive wall time and higher cost cannot be causally attributed to DAG scheduling; they primarily show Luna tail/output variance at `n=1`. The useful performance finding is narrower: deterministic READY/lease/affinity checks introduced no visible startup delay when four independent nodes were available. No p50/p95 or universal speed claim is made.

## Tool-schema cost

The installed four-tool surface measures approximately 1,478 schema tokens. The normal `runtime_info + start_task` path is about 505 tokens, 5.2% above the retained 0.6.4 baseline of 480. The advanced `start_batch` schema is about 749 tokens, 67.6% above its former 447-token shape because it now declares dependencies, leases, affinity, priority, optional nodes, and quorum. That cost stays on the advanced tool surface; it is not evidence of runtime model speed.
