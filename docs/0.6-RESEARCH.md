# Heliolune 0.6 engineering report: token and parallel-speed profiles

This document records the evidence used to accept Heliolune 0.6.0. Historical 0.5.2 measurements are retained as the baseline.

## Questions

1. Where does 0.5.2 still spend avoidable model tokens or wall time?
2. If Luna cache hits are not treated as a goal, can four or eight cold Luna workers materially improve latency at comparable quality?
3. Can the result be exposed as two simple policies without giving Luna control of planning or reserved decisions?

## 0.5.2 token and reliability audit

The persisted 0.5.x dashboard contained 12 successful task runs and 4 failed runs. It recorded 960.155 seconds of worker wall time, 383,593 input tokens, 317,440 cached input tokens, 11,017 output tokens, and an 82.75% input-cache rate. Estimated Luna cost was 0.819995 price units.

The cost split matters more than the headline cache rate:

| Component | Price units | Share |
|---|---:|---:|
| Uncached input | 0.330765 | 40.34% |
| Cached input | 0.158720 | 19.36% |
| Output | 0.330510 | 40.31% |

The shared supervisor/Leader lane accounted for 0.141155 units (17.21%) across two uncached turns. The integration lane spent 0.300690 of its 0.512369 units on output (58.69%). This means cache tuning alone cannot solve the remaining cost problem: terminal reliability, optional model turns, output size, and the Sol-visible MCP schema all matter.

The decisive reliability finding was reproduced during this research. A real worker emitted `turn/completed`, but 0.5.2 matched only `params.turn.id`; the current App Server may identify the same notification with top-level `params.turnId`. Activity tracking saw the completion while the terminal waiter did not, producing `hard_timeout_active`, a needless 180-second wait, and a failed finalization. The research branch normalizes both notification shapes and retains a bounded completed-turn buffer to close the response/waiter race. A focused regression now completes in about 150–170 ms instead of reaching the test hard timeout.

Additional token changes in 0.6.0:

- The inline MCP App and app-only `job_status` tool were removed. The Windows-native panel is the only Heliolune-rendered live surface.
- The duplicate public blocking `run_task` tool was removed; Desktop uses `start_task` or `start_batch`, followed by exactly one `await_task` call.
- Low-frequency supervision/finalization/reporting knobs were removed from the normal token-first tool schema. Safe internal defaults remain.
- Measured serialized tool definitions fell from approximately 2,520 tokens for the pre-change token-first surface to 1,557 tokens for the complete 0.6 surface including speed-first, a 38.2% reduction. The speed-first-only surface is about 1,074 tokens. Character-count divided by four is only an approximation; current Sol controller usage is still not observable at the MCP boundary.

## Parallel benchmark method

Eight independent read-only code-audit workstreams were run with the same response schema. Each measured profile created fresh Luna/max worker threads, so persistent-lane cache reuse was not a requirement. Every profile also paid for one fresh Luna/high Leader aggregation turn. Wall time covers worker execution plus Leader aggregation; initialization is reported separately in the raw artifacts.

The `cacheIgnoredColdEquivalent` field prices every input token at the uncached Luna input rate, even when the service reports a cache hit. It therefore answers the requested cache-independent cost question without pretending cache can be disabled at the API boundary.

## Results

| Luna concurrency | Samples | Wall time | Speedup vs 1 | Quality score | Cache-ignored cold cost |
|---:|---:|---:|---:|---:|---:|
| 1 | 1 | 200.769s | 1.00× | 100% | 0.890920 |
| 4 | 2 | 52.064–53.627s; mean 52.846s | 3.80× | 90–95% | mean 0.816648 |
| 8 | 2 | 36.488–73.225s; mean 54.856s | 3.66× | 95% | mean 0.821255 |

Four workers delivered a stable, near-linear speedup. Eight workers produced the fastest single run (5.50×) but also the slowest parallel run (2.74×) because one worker became a 67.6-second straggler. With only two parallel samples, the variance is more important than the mean: eight-way burst is useful as an explicit latency experiment, not as the default.

The automated quality score is conservative. Parallel deductions came from exact-string checks and one question that scoped a worker to `status-window.mjs` while asking it to prove removal of server-side inline UI. Honest `uncertain` answers were penalized even though they exposed a benchmark-scope defect. All four workstreams in two separate end-to-end MCP smokes completed, and the shared Leader returned a structured report.

Three end-to-end four-worker MCP smokes completed in 44.137s, 49.607s, and 43.843s. Their worker wall times were 29.883s, 35.264s, and 29.681s, while summed worker durations were 99.828s, 111.832s, and 102.530s. The shared Leader added 14.252s, 14.340s, and 14.159s. The second smoke rendered the native WPF panel and published its ready marker; no inline MCP App resource or output template was advertised. The final smoke used the reduced public `start_batch` schema, completed all four workstreams, and cost an estimated 0.225093 Luna price units.

## 0.6 policy

### Token first

- Tool: `start_task`, then one `await_task`.
- One function-affine Luna/max owner per task.
- Persistent `core`, `tests`, `integration`, and `verifier` workers plus one shared Luna/high Leader.
- Adaptive verifier and Leader use; no model polling.
- Supports bounded analysis, implementation, and repair.
- Optimizes stable prefixes, session reuse, compact schemas, and the smallest sufficient result.

### Speed first

- Tool: `start_batch`, then one `await_task`.
- Sol must provide 2–8 independent workstreams with separate scope and acceptance criteria. Luna never plans or decomposes the parent request.
- Four Luna/max burst workers are the default. Eight are allowed only as an explicit experimental choice.
- One shared Luna/high Leader accounts for every terminal outcome and compresses the handoff. It does not inspect the repository, resolve disagreements, or accept results.
- Every workstream has its own hard deadline and failure isolation; one straggler can make the batch partial but cannot discard completed siblings.
- Prefer workstreams sized for 90 seconds or less, but allow bounded deadlines up to 600 seconds. One shared Luna/high Leader session coalesces simultaneous 90-second checks and returns per-slot liveness recommendations; a later queued wave can reuse the same session for another bounded check. It does not plan, redistribute work, or poll. The same warm Leader later compresses the terminal batch.
- Read-only burst sessions may be reused. Every mutating workstream instead receives a fresh Luna/max session in an isolated detached Git worktree.
- Mutating batches require a clean repository root, the current committed `HEAD`, and narrow pairwise-disjoint repository-relative scopes. Heliolune collects full-index Git patches, rejects unexpected or overlapping paths, checks `git apply --check --index`, applies the batch, and leaves the main index unstaged for Sol review.
- A partial/failed worker, a changed main `HEAD`, or a newly dirty main worktree blocks the entire apply. The main checkout stays unchanged and retained patch artifacts are reported to Sol. Repositories are never copied.

## Parallel-write smoke

The release smoke created a temporary Git repository and assigned two real Luna/max workers to disjoint `alpha.txt` and `beta.txt` scopes. Each worker modified its own detached worktree; Heliolune then validated and applied both patches to the clean main checkout.

| Metric | Result |
|---|---:|
| Batch status | completed |
| Safe integration | applied; `alpha.txt`, `beta.txt` |
| Main index after apply | clean / unstaged |
| Remaining Git worktrees | 1 (main only) |
| Worker wall / summed duration | 27.428s / 50.702s |
| Shared Leader | 8.110s |
| End-to-end wall time | 35.541s |
| Luna usage | 44,690 input; 28,160 cached; 666 output; 203 reasoning |
| Estimated Luna cost | 0.116710 price units |

Unit coverage also verifies out-of-scope rejection, dirty-main rejection, changed-`HEAD` rejection, retained patch evidence, untracked-file integration, worktree cleanup, and an unstaged final index.

## Decision

The feature is viable with limits. Four-way speed-first execution materially improves latency and is the 0.6 conditional default whenever Sol identifies at least two independent workstreams. Its mean cache-ignored cold-equivalent cost was 8.34% below the single-worker read-only sample; the two four-way runs were 12.26% and 4.42% lower respectively. With only one serial sample, this is evidence of comparable cost, not a universal saving claim. Eight-way execution remains opt-in until more repetitions demonstrate a better tail distribution. Token-first remains the default for dirty repositories, overlapping or dependent modifications, and small tasks.

The worktree gate resolves the immediate parallel-file safety issue without enabling concurrent writes in the main checkout. Future work should add repeated mixed-size benchmarks, explicit service-concurrency diagnostics, batch dashboard percentiles, and portable status UI coverage.

The measured workstreams finished before the 90-second management checkpoint, so the cost table includes terminal Leader aggregation but not an additional long-task management turn. Long-batch management is covered by scheduling, prompt-boundary, watchdog, and shared-session tests; its incremental cost still needs a dedicated release benchmark.
