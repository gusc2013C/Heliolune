# 0.6.3 runtime and backend diagnostic

English · [简体中文](0.6.3-RUNTIME-DIAGNOSTIC.zh-CN.md)

## Purpose

This diagnostic was designed to find Heliolune defects, not to build a production application. A fresh dependency-free Python repository, ParcelPulse, specified a deterministic inventory-event reconciliation engine, JSONL loader, CLI, and 12 public tests. An eight-test evaluator remained outside the repository and was run only by Sol after integration.

The run also reproduced the user's report that Heliolune had returned to serial Luna execution and opened a Codex window instead of only the floating Leader panel.

## Root cause of the serial/visible-worker regression

The active Codex task had loaded an older Heliolune MCP process before the newer plugin source was installed. Its tool surface exposed legacy `initialize_pool`/`run_task` behavior and lacked the new `runtime_info` identity call. MCP processes and tool schemas are not hot-replaced inside an existing task, so editing or reinstalling the plugin could not change that already loaded runtime.

0.6.3 adds a fail-closed, no-model preflight. Before paid work, the skill requires the loaded runtime to report:

- version `0.6.3`;
- default `speed-first` with parallelism 4;
- ephemeral burst threads;
- a hidden standalone app-server;
- the native Windows status surface.

Any mismatch stops before Luna is started and asks for a new Codex task or app restart. The standalone app-server is launched hidden, worker threads are ephemeral, and the WPF Leader window is the only automatic Windows worker surface.

## Defects found and fixed

1. The parallel contract lane could return an ordinary ambiguity as `needsSol` and interrupt the writer. It now triggers only with `status=blocked` and a non-empty decision that is actually reserved for Sol.
2. Read-only reviewers inspect independent base snapshots by design. Their initial-file observations were being presented as contradictions with a concurrent owner patch. Review prompts and the Leader contract now label them as base-snapshot guidance, while actual change paths and integration records remain authoritative.
3. Codex's command environment selected a stale `C:\Users\Infplane\.gaia\venv\Scripts\python.exe` launcher whose uv-managed interpreter no longer existed. Heliolune now uses the documented shell environment policy to prefer Codex's bundled Python, Node, and Git paths, with the normal host PATH retained as fallback.
4. A 360-second task reserved 90 seconds for structured finalization, leaving too little time for a last test pass. The default reserve is now 40–60 seconds, with a proportional 10–20 second grace for the original turn to finish its own schema.
5. Luna treated unavailable hidden tests as unfinished acceptance and returned `partial` after all supplied tests passed. Completion now means all scoped work and every supplied, runnable acceptance check are complete after the last edit; unknown hidden tests are risks for Sol, not missing Luna work.

The owner completed and Heliolune applied `parcelpulse/engine.py` and `parcelpulse/cli.py` only after clean-state, scope, completion, overlap, and Git apply gates passed. Sol then ran all public tests plus hidden UTC-offset, generator immutability, rejection atomicity, signed-adjust, invalid-type, deterministic-duplicate, iterable-JSONL, stdin, and missing-file checks. Total acceptance was 20/20.

## Interpretation

The final run demonstrates application value for a bounded multi-file backend task: Luna/max produced a correct implementation at low worker cost while Sol retained acceptance. It does not demonstrate a speed win. The 317-second owner remained the critical path, so the parallel reviews improved coverage and did not reduce wall time below the writer. The result supports a cost-first use case with visible progress, not a claim that Heliolune is universally faster than Sol-only.
